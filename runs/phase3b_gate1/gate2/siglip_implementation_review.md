# SigLIP2 implementation check (CPU only)

- **Pinned snapshot:** `google/siglip2-base-patch16-224`, revision `022b6f71160ffb0169ca4709e2d7e25be659598a`. Local processor is `SiglipProcessor` with `GemmaTokenizer` under Transformers 5.19.0.
- **64-token rule:** the actual tokenizer backend has right padding to length 64 and truncation at 64. Processor calls without `max_length` returned five 64-token sequences; adding explicit `max_length=64` yielded byte-for-byte identical IDs. This matches the [official SigLIP2 documentation](https://github.com/huggingface/transformers/blob/main/docs/source/en/model_doc/siglip2.md), which specifies fixed padding/truncation to 64. The pinned checkpoint files identify `SiglipProcessor`/`GemmaTokenizer` and `model_type=siglip`; the tokenizer backend itself supplies the 64-token default.
- **Observed IDs and tokens:** recorded in `tokenization_cpu.json`. Active IDs are `black car` → `[6944, 1226, 1]`; `parking lot` → `[74811, 2940, 1]`; `baseball field` → `[111021, 2725, 1]`. Each has EOS ID 1 followed by 61 PAD IDs 0. The full black-car question has 24 active tokens including EOS; the baseball question has 17. Sequence length is 64 in every case.
- **Attention mask:** the processor returns only `input_ids`; it did not return an attention-mask tensor, and Gate 1 passed no mask to `get_text_features`. In the pinned Transformers 5.19.0 `SiglipTextModel`, a missing mask yields bidirectional attention over the full fixed-length sequence, and pooling uses the final hidden position (which is a PAD token). `tokenization_cpu.json` records an *inferred* non-pad mask (1 for token IDs other than 0, 0 for right padding); it was not the model's actual `attention_mask` input. This fixed-length path is consistent with the documented SigLIP convention, but padding is not explicitly masked in this execution.
- **Special-token warning:** tokenizer configuration gives BOS=2, EOS=1, PAD=0, while the loaded `SiglipTextConfig` carries BOS=49406, EOS=49407, PAD=1. Transformers 5.19.0 warns that BOS/EOS 49406/49407 exceed its default 32k vocabulary range; the checkpoint’s loaded text config reports vocabulary size 256,000 and max positions 64. The input IDs are all in that embedding range. The current `SiglipTextModel` forward path does not choose tokens by its BOS/EOS IDs; it consumes the input IDs, builds a bidirectional mask, and pools the last fixed-length hidden state. No evidence shows these config IDs changed the Gate 1 token IDs or preprocessing.
- **Casing caveat:** tokenizer config declares `do_lower_case: true`, but the loaded `GemmaTokenizer` object has no active `do_lower_case` property and the CPU probe shows `BLACK CAR` and `black car` tokenize differently. The official SigLIP2 documentation describes lowercasing as part of default preprocessing. Gate 1 used lowercase decomposed queries (`black car`, `parking lot`, `baseball field`), so this discrepancy does not affect those exact strings. Future uppercase or full-question encoding should explicitly lowercase or use a processor implementation verified to do so.
- **Images and features:** local image config specifies 224×224 bilinear resize, RGB input, rescale by 1/255 and normalize with mean/std `[0.5, 0.5, 0.5]`. `code/build_feature_cache.py` passes the processor output to `get_image_features`/`get_text_features`, extracts `pooler_output`, casts to float and L2-normalizes. This matches cosine ranking.

No material mismatch was established for the exact lowercase Gate 1 phrases and stored fixed-length inputs; embeddings were not rerun. The checkpoint's config special-token IDs differ from tokenizer IDs, but the pinned text forward path does not use the configured BOS/EOS IDs to select tokens or pool; it embeds the actual tokenizer IDs and pools position 63. CPU-only review did not rerun a model forward pass, so exact feature parity outside the recorded Transformers 5.19.0 execution remains unverified.
